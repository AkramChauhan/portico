How Portico works, and what it costs

Portico is a thin, unprivileged app driving a Caddy server. The design turns on one decision — every site gets a second, plain-HTTP vhost on loopback — and one tradeoff: it installs two small root jobs once and then stops asking for a password. This document covers both, plus the platform traps that look like arbitrary complexity until you know what they defend against.

Status Current Owner akramchauhan Last reviewed 2026-09-14
What is verified here. The request paths, TLS trust and port behaviour below were exercised end to end on a real machine, including a public URL returning 200 with a publicly trusted certificate. Claims that were not tested are marked and listed in the assumptions register on this page.

1 · The two request paths

A browser on this Mac and a webhook sender on the internet arrive by completely different routes, and the only thing that reconciles them is the loopback twin.

2 · Name resolution

Getting a name to resolve is the part that needs the machine's cooperation, and it is where the two modes differ.

NameHow it resolvesCost
app.localhostmacOS resolves *.localhost itself, per RFC 6761Nothing at all — but in System mode the URL carries :18443, see why
app.testdnsmasq wildcard plus /etc/resolver/testOptional — only if dnsmasq is installed
app.ioOne line in the managed block of /etc/hostsOne authorisation at install, then never again
Why dnsmasq is optional. It only buys wildcard *.test names. Every domain works through /etc/hosts, and since the helper writes that without a password, dnsmasq's absence costs a convenience rather than a capability. It has no official macOS binary release, so requiring it would have dragged Homebrew back into the prerequisites for a nicety.

3 · The privilege split

Exactly one thing genuinely requires root on macOS: answering on ports 80 and 443. Everything else has an unprivileged equivalent, and the two modes exist because of that single constraint.

System mode — the default

Caddy runs as you, on loopback ports 18443/18080. Domains resolve to 127.77.0.1, and a pf rule carries that address’s 443 and 80 across, so URLs have no port. One authorisation at install covers the forwarding, DNS and the hosts helper.

Standalone mode

Caddy runs as a user LaunchAgent on :8443. Nothing outside the home folder is touched, except one /etc/hosts line for a custom domain.

Portico never holds port 443. It used to: a root Caddy on 0.0.0.0:443 made Docker fail with ports are not available … bind: address already in use. Now the only thing listening on 443 is whatever else you run, and Portico’s traffic arrives on an address nothing else uses.

Simpler optionWhy it does not work
Keep root Caddy, bind 127.0.0.1:443 onlymacOS refuses another user’s 0.0.0.0:443 bind while root holds the port on any address — EADDRINUSE even with SO_REUSEADDR and SO_REUSEPORT. Tested against a live root listener.
Run Caddy as you on 127.0.0.1:443Unprivileged low-port binds are allowed on the wildcard address only; a specific address fails with EACCES. Tested.
Forward 127.0.0.1:443 instead of an aliasTakes localhost:443 away from Docker, which is the problem being solved.

That last row is also why a .localhost site shows :18443 in System mode. Browsers resolve *.localhost to 127.0.0.1 themselves, without reading /etc/hosts, so the name can never reach the forwarded address. It is served on Caddy’s own port rather than by claiming 443 back.

The forwarding lives in the com.apple/portico anchor, which the stock /etc/pf.conf already evaluates, so no system file is edited. Enabling pf hands back a reference token; Portico keeps exactly one and releases it on uninstall, so pf stays on for anything else that enabled it. Aliases and rules both vanish on restart, which is why a root job re-applies them at every boot (verified across a reboot: /var/log/portico-loopback.log records each run). The doctor proves the path works by asking 127.77.0.1:80 for a hostname no site uses and looking for Portico’s own 404 — an open socket alone could be Docker’s.

The app itself is never privileged. It reconfigures Caddy through the loopback admin API, which is why adding a site is instant and silent — covered in section 9.

4 · Working out what to serve

Point the target at a directory and the type is inferred, so a port is only needed for stacks that require a process of their own.

DetectedHowServed as
PHP projectpublic/index.php or index.phpphp_fastcgi to PHP-FPM, front-controller try_files
JS projectpackage.json with a dev, start or serve scriptPortico runs the dev server and proxies to a port it assigns
Built outputdist/, build/, out/, _site/ containing index.htmlFile server
Ambiguouspackage.json with neither script nor buildRejected with an explanation, rather than a mystifying 404

PHP needs no port because PHP-FPM is already a shared daemon that Caddy speaks FastCGI to. Node has no equivalent, so Portico supervises the dev server itself — which also ends the question of which project owns port 3000.

5 · Public URL providers

ProviderAccountStable hostnameNotes
cloudflared quick — defaultNoneNo — new random name each runVerified anonymous: no config, no login, works first try
cloudflared namedCloudflare API token + your domainYesPer site. Portico creates the tunnel, writes the CNAME to <id>.cfargotunnel.com, and runs it against the same loopback twin
ngrok freeRequiredNoWithout an authtoken the agent refuses to start (ERR_NGROK_4018)
ngrok paidRequiredYes, custom domainPlan is detectable from the assigned hostname: the free tier is always *.ngrok-free.app

cloudflared stays the default precisely because it needs no account. Making ngrok the default would put a sign-up wall in front of the first thing a new user tries, which is the opposite of the zero-prerequisite install.

The fixed hostname is a property of the site, not of the app. It was global once, which was a bug rather than a simplification: two sites publishing at the same time both claimed the one hostname, and the second quietly lost. A config written before the move carries its old value onto the first site that has none, and the global is then cleared so it cannot be handed out twice.

ngrok is entered the same way and stored the same way, but reaches the agent by a different route: a config file of our own, selected with --config. Not --authtoken, which would put the secret in argv; and not ngrok config add-authtoken, which does the same on its way to rewriting the user’s own file. When Portico holds no token it passes no --config at all, so a token the user added with the ngrok CLI keeps working untouched.

The route was chosen the hard way. The obvious answer is NGROK_AUTHTOKEN in the environment, which keeps the secret off disk entirely, and the agent does read it. But ngrok’s default config file takes precedence over that variable. On a machine that already had a valid token in ~/Library/Application Support/ngrok/ngrok.yml, a deliberately invalid token was accepted: the probe connected on the old token, reported success, and stored the bad one. --config replaces the default rather than merging with it, so the token the user typed is the one that actually runs — which is what makes the check below mean anything.

ngrok has no endpoint that answers “is this token valid?”, so connecting is the test: saving one opens a throwaway tunnel, and both the keychain entry and the config file are removed again if that fails. The hostname it gets back also reveals the plan, since the free tier is always on ngrok-free.app — which is why there is no separate “check my plan” action. Entering the token already answers the question.

Neither token leaves the machine. Both live in the login keychain, and Portico has no account and no server of its own to send them to; the only thing that ever sees one is Cloudflare’s or ngrok’s own API. The interface says so next to the fields, because “stored in your keychain” answers where it is kept without answering the question people actually have, which is whether it was uploaded.

The file is schema 3, which nests the token under agent. A bare top-level authtoken is schema 2, and a v3 agent rejects the whole file with field authtoken not found in type config.v3yamlConfig — which reads like a Portico bug rather than a config one.

One trap worth naming. ngrok quotes a rejected authtoken back inside its own error text — “Your authtoken: <value>”. That output is written to tunnel-<site>.log and the last error line is shown in the app, so without care a single mistyped token would sit in plaintext in a file that outlives the mistake. Every line the agent prints is scrubbed of the token before it is written down or surfaced.

The API token lives in the login keychain, not in config.json. That file is written 0644 — protected only by the 0700 directory around it — and is read wholesale on every Config::load(). A token that can edit DNS on a real account does not belong there. It never appears in a command line either: both security and curl receive it on stdin, because everything in argv is visible to any local process through ps.

5b · Reaching a site from another device

Three tiers, and the difference between them is the whole point of being explicit about which one a site is on.

TierWho can reach itAddressTLS
LocalThis Mac onlyhttps://shop.testPortico’s own CA, trusted here
Local networkAnyone on the same networkhttp://192.168.1.5:8801None — plain HTTP
PublicThe entire internethttps://hooks.example.comPublicly trusted, via Cloudflare

The obstacle to LAN sharing is not the listening socket — it is that the other device cannot resolve the name. dnsmasq answers on 127.0.0.1 and returns a loopback address; a phone can neither reach it nor use its answer. Publishing over mDNS or repointing each device’s DNS both work, and both are a setup step per device.

So a shared site gets its own port on every interface instead, and the address handed to the user is a bare IP. Uglier than a hostname, and it works on every device with nothing to configure — the better trade for “open this on my phone for two minutes”. Plain HTTP for the same reason: the certificate is signed by an authority that exists only in this Mac’s trust store, so every other device would warn. A padlock that has to be explained is worse than no padlock.

The first row used to have a caveat. System mode Caddy bound 0.0.0.0:443, so a machine on the same network sending the right Host header to this Mac’s IP was served the site with sharing off (R13). Every vhost now binds loopback in both modes, and the LAN listener is the only socket on another interface — which is what the sharing toggle means.

Unlike a public tunnel, this survives a restart. A quick tunnel is cleared at launch because its hostname is random and the user has never seen it; a LAN port is stable and was chosen deliberately. The cost is that the network at a café is not the network at home, which is why the interface says so next to the switch rather than in a tooltip.

7 · The /etc/hosts helper

The file that triggers the helper is writable by the logged-in user, so its contents are treated as hostile input. The capability granted is real, and bounding it is the entire design:

Only loopback mappings

The sole thing ever written is a mapping to Portico's two fixed loopback addresses, inside Portico's own markers — the address is compiled in, never read from the request. Every other line of /etc/hosts is copied through untouched.

Strict hostname allowlist

Checked before use, so no whitespace, newline or # can break out of a line and forge an entry. Covered by tests that attempt exactly that.

Capped and atomic

At most 200 entries, and the file is replaced by rename so a crash cannot leave it truncated.

Not sudoers, not setuid

A sudoers NOPASSWD rule leaves a standing password-free sudo. Setuid is worse — callable by anything, any time, with the caller's environment. This is neither.

The honest cost. Anything running as you can cause a root-privileged write to /etc/hosts without a password. The worst achievable outcome is pointing a hostname at loopback — which is the feature. It cannot obtain root code execution and cannot modify a line it did not create. That is the price of "stop asking me for a password", and it should be a deliberate choice rather than a surprise.

9 · The admin API

Caddy's admin API listens unauthenticated on 127.0.0.1:2019, so any local process can reconfigure it. This was the largest open risk while System mode ran Caddy as root: reconfiguring it meant serving any file root could read.

Moving Caddy behind a pf redirect — the redesign this section once called substantial — closed it as a side effect of freeing port 443. Caddy runs as you in both modes now, so the admin API grants nothing a local process running as you does not already have. It is still unauthenticated; it is no longer a privilege boundary.

10 · macOS platform traps

None of these are documented anywhere obvious, and each cost a debugging cycle.

BelievedActuallyNow
caddy trust installs the CA when run as root. It shells out to sudo even when already root, which fails with no tty: failed to execute sudo: exit status 1. The root certificate is fetched from Caddy's admin API and installed directly.
Certificate trust can be scripted inside the privileged installer. security add-trusted-cert must present its own authorisation dialog. Nothing launched by do shell script … with administrator privileges can show UI: "the authorization was denied since no user interaction was possible". Trust runs from an ordinary process, in the user trust domain, for both modes.
A launchd job inherits a usable environment. It inherits no HOME. Caddy resolved its data directory to a relative path and failed with mkdir caddy: read-only file system — an error that names neither the real cause nor the real path. Both plists set HOME, XDG_* and a working directory.
launchctl bootout then bootstrap reloads a job. A KeepAlive job respawns faster than one bootout retires it, and bootstrap fails outright on an already-loaded job (Input/output error). Plist edits appeared to do nothing. Every job is retired with a retry loop that waits until it is genuinely gone.
A WatchPaths job fires on every change. ThrottleInterval defaults to 10 seconds. Two edits in quick succession silently skipped the second — which is exactly how removing a site left an orphaned hosts entry. ThrottleInterval set to 1.
Binding root Caddy to 127.0.0.1:443 leaves 0.0.0.0:443 free. xnu rejects a wildcard bind by a different user on a port root holds on any address, whatever the socket options. Docker runs as you, so it still failed. Nothing Portico runs binds 443; pf forwards a dedicated address instead.
Rust CLIs behave in pipelines. Rust aborts on SIGPIPE, so portico ls | head panicked rather than exiting quietly. SIGPIPE reset to default in main.

11 · The recurring bug: state saved before the act succeeded

This shape appeared four separate times and is worth recognising on sight. The code saved configuration, then performed the system change the configuration described. When the change failed or was refused, the two disagreed permanently.

WhereSymptom when it failed
remove_siteSite gone from config, its /etc/hosts line left behind — orphaned, with nothing left that knew the domain existed to clean it up. Reported by a user.
add_siteSite in config but never served.
set_tunnelToggle switched on, nothing running, no error. Read as the app having lost the site. Reported by a user.
set_runSame, for a supervised dev server.
The rule now: perform the system change first, persist only on success. If you find yourself writing cfg.save()? before an apply(), that is this bug again.
